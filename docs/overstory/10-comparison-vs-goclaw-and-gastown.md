# Comparison Vs Goclaw And Gastown

## One-line positioning

- `goclaw` is stronger as a **durable orchestration engine**
- `gastown` is more radical as an **orchestration idea machine**
- `overstory` is strongest as a **local coding swarm substrate with a serious runtime abstraction layer**

## Relative strengths

| Axis | Overstory | Goclaw | Gastown |
|---|---|---|---|
| Durable task engine | Medium | Strongest | Weaker |
| Runtime abstraction | Strongest | Medium | Weak |
| Local coding swarm substrate | Strong | Medium | Strong |
| Worktree discipline | Strong | Medium | Strong |
| Cross-repo orchestration closure | Weak | Medium | Weak |
| Prompt/role architecture | Strong | Medium | Medium |
| Operational predictability | Medium-low | High | Low |
| Architectural honesty | High | Medium | Medium |

## Best comparison sentence

`overstory` feels like the point where:
- `gastown`'s swarm ambition
- meets a much cleaner TypeScript architecture
- but still stops short of `goclaw`'s durable-engine maturity

## What overstory does better than goclaw

- runtime abstraction
- headless / direct-spawn direction
- worktree-first coding substrate
- explicit self-critique of swarm failure modes

## What goclaw does better than overstory

- durable orchestration state machine
- lifecycle closure
- task engine truth
- recovery model around long-running orchestration
- platform-grade subsystem maturity

## What overstory does better than gastown

- cleaner core abstractions
- much better test surface
- more explicit stores and boundaries
- better runtime design taste

## What gastown still does better than overstory

- bolder orchestration imagination
- more radical thinking around agent societies

## Chief-architect takeaway

If building a new orchestrator:
- steal engine durability lessons from `goclaw`
- steal runtime abstraction lessons from `overstory`
- steal idea ambition from `gastown`
- and copy none of their main substrate or boundary mistakes
