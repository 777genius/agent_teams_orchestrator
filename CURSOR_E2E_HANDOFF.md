## 1. Цель

Довести интеграцию Cursor в Agent Teams до состояния, когда она работает
end-to-end в **продукте**, а не только в тестах:

- команда с лидом на Cursor запускается через десктопное приложение (`dev:mcp`);
- агенты решают задачи (правят файлы, выполняют команды);
- агенты общаются между собой (команда из лида и напарника);
- App MCP (инструменты Agent Teams) доступны агенту;
- Stop реально останавливает работу, без поздних записей;
- соседняя сессия при этом продолжает работать.

Формулировка пользователя: «Проверишь через dev:mcp команду с курсор агентов что
они решают задачи, что они общаются между собой и всё-всё».

## 3. Что такое managed Cursor в двух абзацах

Cursor подключён к OpenCode через плагин `@rama_nigg/open-cursor@2.5.2`, который
выставляет Cursor как OpenAI-совместимого провайдера. Приложение собирает этот
плагин в проверяемый артефакт (`scripts/cursor-plugin/`), применяет небольшой
ревьюабельный патч (`scripts/cursor-plugin/cancellation.patch`), выдаёт каждому
профилю свой прокси-порт, материализует конфиг там, где мост плагина его читает,
и привязывает готовность к живой нативной учётной записи Cursor.

Режим `TOOL_LOOP_MODE=opencode`: OpenCode исполняет инструменты, а cursor-agent
крутит только ходы модели. **Но это не абсолют** — см. раздел 7 про разрешения:
агент может выбрать и свой родной `shell`.

Ничего не включается, пока не проверены staged-ассеты: иначе используется
апстрим-плагин и сегодняшний путь запуска без изменений.

## 4. Окружение: как поднять и не сойти с ума

Здесь я потерял больше всего времени. Читай внимательно.

### 4.1. На машине одновременно работают несколько приложений Agent Teams

Пользователь предупредил: **другой агент параллельно тестирует ZAI**. У него
свои экземпляры Electron. Плюс может быть запущено приложение самого
пользователя. Итого 2–3 инстанса.

Последствия, которые меня укусили:

- **Порты отладки разъезжаются.** `pnpm dev:mcp` жёстко просит 9222; если он
  занят, Electron берёт следующий свободный (9223, 9224…). Мой хелпер сначала
  «пробовал порты по очереди» — и я несколько часов управлял **чужим**
  приложением, не понимая, почему в нём старые сообщения об ошибках и пропадают
  созданные команды.
- **Общий `~/.claude` даёт `database is locked`** и таймауты воркеров, после
  чего мой инстанс падал.

### 4.2. Правильный способ: изолированный инстанс

В приложении есть штатные dev-переменные изоляции
(`src/main/utils/electronDevPathOverrides.ts`):

- `AGENT_TEAMS_ELECTRON_CLAUDE_ROOT` — отдельный корень вместо `~/.claude`;
- `AGENT_TEAMS_ELECTRON_USER_DATA_DIR` — отдельный userData Electron.

Рабочая команда (из worktree фронта):

```bash
SCRATCH=<любой каталог для мусора>
ORCH=/Users/belief/dev/projects/claude/_worktrees/agent-teams-orchestrator-cursor-managed-pr

AGENT_TEAMS_ELECTRON_CLAUDE_ROOT="$SCRATCH/claude-root" \
AGENT_TEAMS_ELECTRON_USER_DATA_DIR="$SCRATCH/userdata" \
CLAUDE_AGENT_TEAMS_ORCHESTRATOR_CLI_PATH="$ORCH/cli-dev" \
nohup node ./scripts/dev-with-runtime.mjs --remoteDebuggingPort 9333 > "$SCRATCH/dev-app.log" 2>&1 &
```

**Важно:** `HOME` менять нельзя. Я пробовал изолировать HOME целиком — Cursor
теряет учётки и падает с `Authentication required. Please run 'agent login'`.
Симлинки на `~/.cursor` и `~/.local` не помогли.

**Порт узнавай не из флага, а из файла**: с отдельным userData Electron всё
равно может взять другой порт. Реальный порт лежит в
`$SCRATCH/userdata/DevToolsActivePort` (первая строка). У меня в итоге был 9336,
хотя просил 9333.

### 4.3. Как рантайм оркестратора попадает в приложение

`scripts/dev-with-runtime.mjs` резолвит рантайм так:

1. `CLAUDE_AGENT_TEAMS_ORCHESTRATOR_CLI_PATH` — явный путь (используй его);
2. иначе `CLAUDE_DEV_RUNTIME_ROOT` — **другой чекаут**, который он сам соберёт;
3. иначе — скачанный релизный рантайм.

⚠️ В окружении сессии уже выставлен `CLAUDE_DEV_RUNTIME_ROOT=/Users/belief/dev/projects/claude/agent_teams_orchestrator`
— это **не наш** worktree, там старый код. Всегда задавай явный путь.

Проверка, что приложение взяло нужную сборку: в логе строка
`Using runtime from explicit runtime override …` и `Runtime version: …`.
Сверяй версию с `grep -o '2\.1\.251-dev\.[0-9]*\.t[0-9]*\.sha[a-f0-9]*' dist/local-cli-dev/cli.js`.

После правки кода оркестратора: `bun run build:dev` **и перезапуск приложения**.

### 4.4. Хелпер управления приложением

`.cdp-e2e.mjs` в worktree фронта. Подключается по DevTools-протоколу и выполняет
одну JS-строку в окне приложения, чтобы дёргать настоящий IPC:


Умеет ждать появления приложения (`CDP_WAIT_MS`). Выбирает страницу по
`http://localhost…`, а не первую попавшуюся (иначе попадёшь в DevTools).

**Не делай так, как делал я:** не опрашивай готовность приложения циклом в шелле,
поднимая новый `node` каждые несколько секунд. Жди внутри страницы одним вызовом.

## 5. Что уже сделано (и почему именно так)

Все правки — на ветке `feat/cursor-managed-launch-and-stop`.

### 5.1. Дубликат плагина в конфиге → `selected_config_match:plugin`

**Симптом:** запуск падал на гейте готовности с `selected_config_match:plugin`.

**Причина:** мост плагина читает MCP-серверы только из **файла** конфига, а
приложение передаёт конфиг через `OPENCODE_CONFIG_CONTENT`. Я материализовал
файл — но записывал туда **весь** managed config. OpenCode **сливает** файл с
содержимым переменной: объекты сливаются по ключам, а **массивы дописываются**.
Плагин попадал в список дважды, и authority отбивал хост.

**Решение:** писать в файл только те разделы, которые мост реально читает
(`mcp`, `agent`), и никогда `plugin`.
Файл: `src/services/opencode/OpenCodeProfileManager.ts`.
Регрессия закрыта в `OpenCodeCursorManagedStop.fake-e2e.test.ts` (проверка, что
в файле нет ключа `plugin`).

### 5.2. Три гейта запуска не согласованы

**Симптом:** запуск проходил readiness, но падал на рукопожатии с другим текстом.

**Причина:** разрешение для Cursor я открыл только в `runReadiness`, а
`launch_runtime` и `launch handshake` продолжали отказывать.

**Решение:** общая функция `resolveManagedCursorLaunchSupport`, все три гейта
спрашивают одно и то же. Файл: `src/services/opencode/OpenCodeBridgeCommandHandler.ts`.

### 5.3. App MCP по HTTP не подключался вообще

**Симптом в логе плагина:**
`MCP server connection failed {"error":"Remote MCP transport not yet implemented for agent-teams"}`.

**Причина:** приложение регистрирует Agent Teams MCP по **HTTP**
(`CLAUDE_MULTIMODEL_AGENT_TEAMS_MCP_URL`), а общий MCP-manager плагина умел
только stdio (`src/mcp/client-manager.ts:46` в апстриме). Мои тесты проходили,
потому что поднимали локальный stdio-сервер — то есть тестировали не тот
транспорт, который использует продукт.

**Решение:** в патч плагина добавлен `StreamableHTTPClientTransport`. Это чинит
**оба** маршрута сразу — и мост (нативные инструменты `mcp__agent_teams__*`), и
CLI `mcptool`. В бандл `mcptool` добавлен статический импорт транспорта
(`scripts/cursor-plugin/build.ts`).

**Подтверждение из продукта:** та же строка лога стала
`MCP server connected {"server":"agent-teams","tools":48}`.

Фейковый E2E переведён на HTTP-транспорт (был stdio).

### 5.4. `mcptool` сообщал об ошибке кодом 0

**Причина:** `connectServer` глотает ошибку подключения (логирует и выходит),
затем `callTool` возвращает строку `Error: … not connected`, а CLI печатал её и
выходил с кодом 0. Агент видел «успех».

**Решение:** проверка `manager.connectedServers.includes(...)` и выход с кодом 1.
В том же патче.

### 5.5. Ручное подтверждение инструментов для Cursor невозможно

Это **измеренный** результат, а не предположение. См. раздел 7.

**Решение:** приложение честно **отказывает** при выборе ручного режима с
провайдером Cursor — на входе `prepareProfile`, до любой работы. Авто-режим и
другие провайдеры не затронуты.

**Важная деталь:** этот отказ сначала сломал **пробную** подготовку профиля в
`prepareProfileForSessionRecord` (она лишь спрашивает «не была ли сессия
manual?»). Теперь отказ там трактуется как ответ «нет», а не как исключение.
Файл: `src/services/opencode/OpenCodeSessionBridge.ts`.

### 5.6. Доставка ассетов

- Сборка (`scripts/build.ts`) стейджит ассеты рядом с рантаймом
  (`dist/cursor-managed`).
- `scripts/cursor-plugin/stage.ts` сам ставит зависимости плагина, иначе
  `bun run build` падал на чистом клоне.
- Резолвер ассетов ищет каталог рядом с исполняемым файлом **и рядом с бандлом**
  (в dev рантайм запускается интерпретатором, поэтому `process.execPath` не
  годится). Проверка владельца и прав: `stat` (а не `lstat`, чтобы идти по
  симлинку) плюс требование каталога — симлинк на каталог `0777` отвергается.
- Релизные архивы (tar, zip, pwsh в `.github/workflows/release-runtime.yml`)
  кладут `cursor-managed` рядом с бинарём и **падают**, если его нет.

### 5.7. Readiness перестал быть бесполезным

`AGENT_TEAMS_CURSOR_READINESS` публиковался в окружение профиля и **никем не
читался**: запущенный хост переживал смену аккаунта. Теперь это сегмент
идентичности хоста, а при переиспользовании с переданным `hostKey` работает
`assertOpenCodeHostReuseIdentity` (этот путь раньше обходил вычисление ключа).

### 5.8. Поиск интерпретатора и поиск `cursor-agent`

Два дефекта одного класса — **предположения об окружении**:

- Интерпретатор для `mcptool` искался только по `PATH` из переданного окружения.
  Приложение отдаёт рантайму курированное окружение, где интерпретатора может не
  быть → managed Cursor тихо выключался, и отказ был неотличим от «ассеты не
  staged». Теперь: PATH вызывающего → PATH процесса → сам процесс.
- `cursor-agent` искался только по `PATH`. Cursor ставит CLI в `~/.local/bin`, а
  macOS-приложение наследует короткий системный `PATH` → на машине, где
  пользователь весь день работает с Cursor, рантайм отвечал «нет CLI» и запуск
  падал как неаутентифицированный. Теперь проверяются известные места установки,
  причём `HOME` вызывающего важнее собственного `PATH` процесса.
  Файл: `src/services/opencode/OpenCodeCursorNativeAuthority.ts`.

### 5.9. Сравнение не той идентичности для Cursor

**Симптом:** `auth_identity_mismatch, auth_state_not_ok` даже после успешной
проверки модели.

**Причина (доказана данными):** в исходном хранилище OpenCode
(`~/.local/share/opencode/auth.json`) провайдера `cursor-acp` **нет вообще** —
там только `openai`. А в управляемой копии профиля остался его credential от
прежней схемы. Сравнение credential-идентичностей давало расхождение, хотя
аккаунт валиден.

**Решение:** Cursor аутентифицируется своей нативной учёткой, а не credential
OpenCode. Когда ассеты проверены и нативный аккаунт авторизован, идентичность
берётся из нативного аккаунта. Это не ослабление strict-проверок: для Cursor это
более сильный признак, чем сравнение несуществующего credential.

### 5.10. Диагностика вместо гадания по хешам

Это отдельная ценность: почти каждый отказ раньше был непрозрачным.

- `selected_config_match` называет разошедшиеся поля.
- Устаревание сессии: `managed_config_changed:<секции>:<hash>-><hash>` —
  посекционные отпечатки пишутся в запись сессии.
- `managed_auth_changed:profile_root | selected_identity | source_store | managed_store_bytes`.
- Отказ extension-bound несёт причину: `(managed path unavailable: not_staged |
  no_interpreter | plugin_artifact_mismatch | unsupported_platform | …)`.
- Сбой bootstrap называет провалившуюся authority-проверку, а не только
  «behavior changed».
- Строгий гейт аутентификации называет условие: `not_cursor_native_candidate |
  managed_assets_unavailable | cursor_account_not_authorized`.

⚠️ Одно ограничение соблюдено намеренно: текст исключения из authority **не**
раскрывается (в нём могут быть учётки/конфиг) — только класс ошибки и фаза.
Не «чини» это.

### 5.11. Бюджет запуска (фронтенд)

`NATIVE_SUBSCRIPTION_CLI_LAUNCH_TIMEOUT_PER_MEMBER_MS` был 90 секунд. Один ход
Cursor измеренно занимает 40–250 секунд, поэтому команда из двух участников не
успевала пройти bootstrap. Поднято до 240 секунд (потолок 10 минут прежний).
Файл: `src/main/services/team/opencode/bridge/OpenCodeReadinessTimeoutPolicy.ts`,
тест обновлён.

## 7. Разрешения: измеренный результат, который надо знать

Спайк в песочнице: `toolApprovalMode: 'manual'`, `--force` выключен, три хода
(shell отклонён / shell разрешён / MCP).

Результат: **запроса на подтверждение не было ни разу**, эффект происходил в том
числе в ходе, который «отклонили». Инструмент в транскрипте назывался `shell` —
это родной инструмент cursor-agent, он исполняет его сам, до OpenCode вызов не
доходит, а правила разрешений OpenCode ключуются на `bash`.

Позже живой прогон той же задачи прошёл через `bash` OpenCode три раза и `shell`
не трогал вовсе.

**Вывод, который надо держать в голове:** агент **сам выбирает исполнителя** на
каждый вызов, и один из двух вариантов молча обходит подтверждение. Режим,
который работает только когда модель случайно выбрала «правильный» инструмент,
— не гарантия. Поэтому приложение отказывает честно.

Следствие для Stop: аргумент «все инструменты исполняет OpenCode» **опровергнут**.
Stop надо доказывать в том числе на нативном `shell`.

## 9. Мой личный план, как я бы это доводил

Порядок именно такой — он минимизирует потери времени.

**Шаг 0. Сначала окружение, потом код.** Подними изолированный инстанс
(раздел 4.2), убедись по `DevToolsActivePort`, что говоришь со **своим**
приложением, и проверь версию рантайма в логе. Если пропустить этот шаг, любые
выводы будут мусором — я на этом потерял часы.

**Шаг 1. Соло-команда как якорь.** Прогони сначала одного агента: `testModel` →
запуск → задача с правкой файла → ответ. Это уже работало, и это дешёвая
проверка, что окружение и сборка в порядке. Если сломалось — чини это, не
переходя дальше.

**Шаг 2. Пара агентов.** Добавь напарника и запусти. Ожидаемые места, где может
упереться: бюджет запуска (уже поднят до 240 с/участник — если снова упрётся,
смотри, какая фаза съедает время, и поднимай осознанно, а не вслепую), и
вторичная линия напарника (в CLAUDE.md есть раздел про secondary lanes и

**Шаг 3. Общение между агентами.** Дай лиду задачу, которую он обязан
делегировать (например: «попроси coder создать файл X и дождись подтверждения»).
Проверяй не по «выглядит правильно», а по данным: сообщения в
`getMessagesPage`, inbox-файлы, и фактический результат в файловой системе.

**Шаг 4. MCP ровно один раз.** Задача, требующая инструмента Agent Teams
(например создать таск с уникальным заголовком). Считай вызовы, а не «получилось

**Шаг 5. Stop.** Запусти заведомо долгую команду и останови. Проверь: процесс

отдельно добейся, чтобы агент воспользовался **нативным** `shell` (например
попроси выполнить команду так, как он сам сочтёт нужным, и убедись по
транскрипту, что это `shell`), и повтори Stop на этом случае.

**Шаг 6. Уборка и оформление.** Открыть PR фронтенда, снять draft с #67,
дождаться CI, обновить `docs/cursor-handoff-evidence/managed-cursor-integration.md`
разделами «что нашёл продуктовый прогон» и «что осталось».

### Принципы, которые окупились

1. **Не гадай — заставь систему назвать причину.** Каждый раз, когда я добавлял
   в отказ конкретное поле/условие, следующий шаг находился за минуты вместо
   часов. Если упрёшься в непрозрачный отказ — сначала сделай его прозрачным,
   это дешевле любой другой гипотезы.
2. **Негативный контроль обязателен.** После каждой правки проверяй, что тест
   падает без неё. У меня так подтвердились: скользящее окно кэша авторизации,
   дубль плагина, отказ manual-режима.
3. **Тестируй тот транспорт и то окружение, что в продукте.** Мои stdio-тесты
   были зелёными, пока продукт вообще не мог подключиться по HTTP.
4. **Проверяй, с кем ты разговариваешь.** Порт, инстанс, корень данных, версия
   сборки. Три раза я делал выводы по данным чужого приложения.

### Чего я бы не делал

- Не возвращать большой нативный supervisor (компилируемый gate, контрольный
  сокет, sweep потомков). Он был удалён осознанно: на macOS SIP скрывает
  окружение платформенных бинарей, поэтому центральное утверждение того подхода
  было ложным, а обычный `client.abortSession()` измеренно завершает процесс
  агента. Подробности — в разделе 5 evidence-документа.
- Не ослаблять strict-проверки ради прохождения запуска. Все мои правки либо
  чинят неверный признак (5.9), либо чинят предположение об окружении (5.8),
  либо делают отказ объяснимым.
- Не раскрывать тексты исключений authority.

### 12.2. Свой прокси-порт на профиль (это был настоящий дефект)

Курируемый каталог прибивал эндпоинт провайдера Cursor к единственному
общеизвестному порту плагина — **32124**
(`OpenCodeCuratedSubscriptionCatalog.ts:504`). Любой чужой или зависший держатель
этого порта молча получал трафик другого профиля и отвечал отказом, а в OpenCode
это выглядело как `AI_APICallError: Internal Server Error`. Утёкший тестовый
прокси на этом порту делал баг воспроизводимым и, судя по всему, был причиной
более раннего репорта «managed transport timed out».

Решение: `src/services/opencode/OpenCodeCursorManagedPort.ts` — каждый профиль
удерживает свой порт (`proxy-port.json` в каталоге ассетов профиля), эндпоинт
провайдера и цель привязки плагина двигаются вместе, и плагин **падает громко**,
а не откатывается на порт, куда никто не позвонит. Проверено против враждебного
сквоттера на 32124, отвечающего 500: профиль занял свой порт и ход прошёл.

Тесты: `OpenCodeCursorManagedPort.test.ts`.

### 12.3. Модель проверки ассетов

`src/services/opencode/OpenCodeCursorManagedAssets.ts` сверяет staged-артефакт
плагина и `mcptool` с дайджестами из манифеста и **падает закрыто** с одной из
причин: `unsupported_platform | not_staged | plugin_artifact_mismatch |
no_interpreter`. Эти же причины теперь попадают в текст отказа (раздел 5.10).

Переменная `AGENT_TEAMS_CURSOR_MANAGED_ASSETS` задаёт корень ассетов явно —
удобно в разработке. Если не задана, ищется рядом с исполняемым файлом и рядом с
бандлом (раздел 5.6). Платформа сейчас только darwin (arm64/x64).

Слабое место, о котором надо знать честно: манифест лежит **внутри** того же
каталога, то есть он самозаверяющий. Кто контролирует каталог — контролирует
плагин. Поэтому и появилась проверка владельца и прав каталога. Это тот же
уровень доверия, что и у явной переменной окружения, но новый риск —
«подхватить посторонний каталог рядом с бинарём» — закрыт.

### 12.4. Три дефекта пробы авторизации, которые уже исправлены

Их легко сломать обратно, поэтому фиксирую:

1. **Скользящее окно кэша.** Запись `recentProbe` обновлялась при каждом
   обращении, поэтому окно свежести ползло: при равномерном трафике разлогиненный
   аккаунт выглядел бы валидным бесконечно. Теперь свежесть считается **от самой
   пробы**. Негативный контроль: с возвращённым багом тест падает.
   Осталось только 5-секундное подавление всплесков внутри одной
   последовательности запуска (`CURSOR_NATIVE_AUTHORITY_DEDUPE_MS`).
2. **`"Not logged in"` содержит `"logged in"`.** Проба считала разлогиненный CLI
   аутентифицированным. Теперь отдельно отбрасывается
   `/\bnot logged in\b|"authenticated"\s*:\s*false/i`. Баг был и в старой пробе,
   не только в новой.
3. **Хешировался сгенерированный wrapper.** Идентичность бинаря считалась по
   обёртке, которую переписывают при каждой подготовке профиля, — это дёргало
   readiness и тратило подпроцесс на каждый запуск. Теперь хешируется реальный
   нативный бинарь (`resolveCursorExecutableIdentity` идёт по `realpath`).

### 12.5. Что именно лежит в патче плагина

`scripts/cursor-plugin/cancellation.patch` трогает три файла. Патч намеренно
маленький и ревьюабельный:

`src/plugin.ts`

- **Привязка к своему порту.** `Bun.serve` слушает
  `AGENT_TEAMS_CURSOR_PROXY_PORT` без молчаливого отката (см. 12.2).
- **Отмена запроса.** По `req.signal` дочерний процесс убивается — это то, на чём
  держится Stop: транспортный abort доводится до cursor-agent.
- **`--trust`, когда `--force` выключен.** Отдельный найденный дефект: без
  `--force` плагин не передавал вообще ничего, и каждый ход умирал на
  `⚠ Workspace Trust Required`. `--force` смешивает два решения — доверие
  каталогу и авто-одобрение любых вызовов; выключение авто-одобрения не должно
  заставлять агента отказываться от каталога, на который его направили.

`src/cli/mcptool.ts` — код возврата при неудачном подключении (5.4).

`src/mcp/client-manager.ts` — HTTP-транспорт (5.3).

Патч применяется как **единое целое** (`git apply` в `scripts/cursor-plugin/build.ts`),
поэтому «снять один хунк для негативного контроля» не получится — стадия сборки
просто упадёт. Мой негативный контроль для HTTP — это строка из продуктового лога
до и после, а не синтетический прогон.

### 12.6. Как сейчас работает Stop

Обычный `client.abortSession(...)` в `OpenCodeSessionBridge.ts`. Никакой особой
машинерии. Измерено: плагин отменяет запрос по сигналу транспорта, дочерний
cursor-agent умирает вместе с ним, поздних записей нет.

Что **намеренно** вне области: потомок, который сам отсоединился от агента, не
разыскивается. Ни один провайдер в приложении так не делает, macOS не даёт
гарантий без root или EndpointSecurity, и если продукту это когда-нибудь
понадобится — место такому решению одно, на уровне приложения для всех рантаймов,
а не внутри одного провайдера.

Напоминание из раздела 7: Stop всё равно надо доказать на нативном `shell`.

### 12.7. Квота Cursor — расходуемый ресурс, планируй прогоны

За сессию я исчерпал **два** аккаунта. Каждый запуск команды тратит ход на
bootstrap каждого участника, плюс `testModel` тратит ход, плюс каждая задача.
Один ход занимает 40–250 секунд.

Практические выводы:

- Не гоняй запуск «на всякий случай». Сначала убедись, что окружение то самое
  (раздел 4), иначе сожжёшь квоту на диагностику чужого инстанса, как я.
- `testModel` нужен после смены аккаунта — он записывает доказательство
  исполнения, без которого гейт запуска откажет.
- Признак исчерпания: `ActionRequiredError: You've hit your usage limit` в
  трассе запуска или в ответе CLI.

### 12.10. Исходник хелпера (он неотслеживаемый — сохрани себе)

`.cdp-e2e.mjs` лежит в worktree фронта и не закоммичен, поэтому дублирую целиком.
Запускать из worktree фронта (там есть зависимость `ws`).

```js
import http from 'node:http'
import WebSocket from 'ws'

const expression = process.argv[2]
// One connection that waits inside the page beats a shell loop that pays node's
// startup cost every few seconds just to ask whether the app is up yet.
const waitMs = Number(process.env.CDP_WAIT_MS ?? 0)
const fetchTargets = port => new Promise((resolve, reject) => {
  http.get(`http://127.0.0.1:${port}/json/list`, res => {
    let body = ''
    res.on('data', c => { body += c })
    res.on('end', () => { try { resolve(JSON.parse(body)) } catch (error) { reject(error) } })
  }).on('error', reject)
})
// Pinned on purpose: another Agent Teams dev app can hold the default port, and
// probing means driving whichever instance answered first. Read the real port
// from <userDataDir>/DevToolsActivePort.
const port = process.env.CDP_PORT ?? 9223
const deadline = Date.now() + waitMs
let targets = null
for (;;) {
  targets = await fetchTargets(port).catch(() => null)
  if (targets?.some(target => /^https?:\/\/localhost/.test(target.url ?? ''))) break
  targets = null
  if (Date.now() >= deadline) throw new Error(`No Electron CDP endpoint on ${port}`)
  await new Promise(resolve => setTimeout(resolve, 2000))
}
// DevTools and a not-yet-initialised window both answer as pages, and the
// second one has no IPC handlers yet, which reads as "the app is broken".
const page = targets.find(t => t.type === 'page' && /^https?:\/\/localhost/.test(t.url ?? ''))
  ?? targets.find(t => t.type === 'page' && t.title !== 'DevTools')
if (!page) throw new Error('No renderer page target')
const socket = new WebSocket(page.webSocketDebuggerUrl, { maxPayload: 64 * 1024 * 1024 })
await new Promise(resolve => socket.once('open', resolve))
const result = await new Promise((resolve, reject) => {
  socket.on('message', raw => {
    const message = JSON.parse(raw.toString())
    if (message.id !== 1) return
    if (message.error) reject(new Error(JSON.stringify(message.error)))
    else resolve(message.result)
  })
  socket.send(JSON.stringify({
    id: 1, method: 'Runtime.evaluate',
    params: { expression, awaitPromise: true, returnByValue: true, timeout: 600000 },
  }))
})
socket.close()
if (result.exceptionDetails) {
  console.log('EXCEPTION:', JSON.stringify(result.exceptionDetails).slice(0, 1500))
  process.exit(1)
}
console.log(typeof result.result.value === 'string'
  ? result.result.value
  : JSON.stringify(result.result.value, null, 1))
```

Использование:

```bash
CDP_PORT=<порт из DevToolsActivePort> CDP_WAIT_MS=120000 \
  node .cdp-e2e.mjs "window.electronAPI.teams.list().then(t => JSON.stringify(t).length)"
```

### 12.11. Вход в Cursor: только руками пользователя

Логин интерактивный, агент сам его не пройдёт:

```bash
cursor-agent login       # печатает ссылку вида https://cursor.com/loginDeepControl?...
```

Ссылку надо отдать пользователю, он открывает её в браузере и выбирает аккаунт.
Окно ожидания — час, поэтому запускай логин в фоне и не держи на нём таймаут.
Проверка состояния без раскрытия деталей:

```bash
cursor-agent status | grep -c "logged in"
```

⚠️ Не передавай `cursor-agent --model <имя>`: это перезаписывает
`~/.cursor/cli-config.json` пользователя (модель и историю выбора). Я так один раз
сделал и восстанавливал вручную.
